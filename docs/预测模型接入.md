# 把训练好的预测模型接进来

调用方（订货建议、`/api/forecast/*`、Agent 工具）只依赖 `backend/forecast/models.py` 里的
`Forecaster` 接口。**换模型实现不需要改任何调用方代码**，也不需要改 Agent Core。

当前仓库里的 `BaselineForecaster`（移动平均 + 星期季节因子）只是把链路跑通用的占位实现，
可以直接替换。

## 一、要实现的接口

```python
from backend.forecast import Forecaster

class MyForecaster(Forecaster):
    name = "lgbm-v1"          # 会写进每次订货建议的审计记录
    version = "1"             # 训练时通常在 fit() 里改成带日期的版本号
    granularity = "sku-day"   # 仅作说明，接口本身不预设粒度
    default_horizon_days = 30

    def fit(self, dataset): ...
    def predict(self, keys, horizon_days, *, start_date=None): ...
```

### `fit(dataset)`

`dataset` 是 `DemandDataset`：

| 成员 | 说明 |
|---|---|
| `dataset.records` | `[{"key": "SKU", "date": "2026-08-11", "qty": 12.0}, ...]`，已按 key + date 排序 |
| `dataset.keys` | 全部 key |
| `dataset.series(key)` | 该 key 的逐日序列，**缺失日已补 0** |
| `dataset.start` / `dataset.end` | 数据窗口 |
| `dataset.summary()` | 行数、key 数、窗口、总量，会写进工件元数据 |

历史不足、数据为空这类情况请抛 `ForecastError`，不要静默返回一个空模型——
宁缺毋滥是这个项目的一致做法。

建议在 `fit()` 结束时把 `self.version` 设成可追溯的值（例如 `f"{dataset.end}-lgbm1"`）。

### `predict(keys, horizon_days, *, start_date=None)`

必须返回逐 key 逐日的列表：

```python
[{"key": "SKU-1", "date": "2026-08-11", "p50": 13.4, "p10": 7.2, "p90": 19.7}, ...]
```

三条硬约束，破坏了订货建议就会算错：

1. `p10 ≤ p50 ≤ p90`，且都 **不为负**；
2. **模型没见过的 key 直接不返回**，不要拿全局均值兜底——上层会把它列进 `skipped` 并告诉员工；
3. `p90 − p10` 是真实的不确定性区间。安全库存就是用 `σ = (p90 − p10) / 2.5631` 折算的，
   区间给太窄会系统性低估安全库存。

### 存取：两种做法，选一种

**A. 参数能 JSON 序列化**（推荐，工件可读、可 diff）：只实现 `state()` / `restore()`，
基类的 `save()` / `load()` 会把它写成 `model.json`。

```python
    def state(self):
        return {"levels": self.levels, "params": self.params}

    def restore(self, state):
        self.levels = state["levels"]
        self.params = state["params"]
```

**B. 二进制权重**（LightGBM booster、joblib、torch）：直接重写 `save()` / `load()`。

```python
    def save(self, directory):
        directory = Path(directory)
        directory.mkdir(parents=True, exist_ok=True)
        self.booster.save_model(str(directory / "model.txt"))
        (directory / "meta.json").write_text(json.dumps({"keys": self.keys}), encoding="utf-8")

    @classmethod
    def load(cls, directory):
        import lightgbm
        model = cls()
        model.booster = lightgbm.Booster(model_file=str(Path(directory) / "model.txt"))
        model.keys = json.loads((Path(directory) / "meta.json").read_text(encoding="utf-8"))["keys"]
        return model
```

另外建议实现 `known_keys()` 返回训练过的 key 列表：员工问到没有历史的 SKU 时，
上层能提前说清楚而不是给出一个看似正常的数字。

## 二、训练并落工件

`scripts/train_forecast_model.py` 用 `--forecaster 模块:类名` 加载任何实现：

```bash
# 先用导出的销售明细 CSV 打通（列名能自动识别常见中文表头，识别不了就用
# --key-field/--date-field/--qty-field 指定）
.venv/bin/python scripts/train_forecast_model.py --csv 销量明细导出.csv

# 换成自己的实现
.venv/bin/python scripts/train_forecast_model.py \
  --csv 销量明细导出.csv \
  --forecaster mymodels.lgbm:LgbmForecaster \
  --holdout-days 14

# 销售表进实时库后（.env 里配好 FORECAST_SALES_TABLE 等）
.venv/bin/python scripts/train_forecast_model.py --days 365 --forecaster mymodels.lgbm:LgbmForecaster
```

把模型类放在仓库根目录能导入的位置即可（比如新建 `mymodels/lgbm.py`），
训练脚本已经把仓库根加进 `sys.path`。

工件落在 `FORECAST_MODEL_DIR/<version>/`（默认 `data/models/`，已 gitignore）：

```
data/models/
  latest                     # 指向当前生效版本
  2026-08-10-lgbm1/
    model.json 或 model.txt  # 由你的 save() 决定
    metadata.json            # 版本、forecaster 引用、训练窗口、回测指标、数据集摘要
```

`metadata.json` 里的 `forecaster` 字段就是 `模块:类名`，服务端据此把实现加载回来。
**这是唯一的耦合点**，其他地方都不用动。

也完全可以不用这个脚本：在自己的训练流程里直接调

```python
from backend.forecast import ForecastStore
ForecastStore("data/models").save(model, version="2026-08-10-lgbm1",
                                 metadata={"metrics": {...}, "features": [...]})
```

## 三、生效与验证

服务端惰性加载最新工件，不需要重启：

```bash
curl -s -H "Authorization: Bearer $AGENT_API_TOKEN" http://127.0.0.1:8777/api/forecast/status
curl -s -X POST -H "Authorization: Bearer $AGENT_API_TOKEN" -H 'Content-Type: application/json' \
  -d '{"keys":["BH25701004-02202"],"horizonDays":7}' http://127.0.0.1:8777/api/forecast/predict
curl -s -X POST -H "Authorization: Bearer $AGENT_API_TOKEN" http://127.0.0.1:8777/api/forecast/reload
```

`/api/forecast/status` 会回报当前版本、`forecaster` 引用、训练时间和回测指标；
`reload` 强制重新加载（换版本后想立刻生效时用）。

每次订货建议都会在 Agent 业务库的 `forecast_runs` 里记下**模型名 + 版本 + 输入快照**，
事后可以复现是哪一版模型给出的建议。

## 四、订货建议还缺什么

预测能跑不等于建议能上线。订货建议的公式是

```
建议下单量 = 交期内预测需求(∑p50) + 安全库存(z×√∑σ²) − 可用库存 − 在途待入库
建议下单日 = 需求缺口出现日 − 供应商交期 − 缓冲天数
```

三项输入的现状：

| 输入 | 现状 |
|---|---|
| 预测需求 / 区间 | 模型工件，本文档说的就是这块 |
| 在途待入库 | **已可用**，从现有采购明细算（数量 − 已入库，排除已取消单） |
| 可用库存 | **还没有数据源**。配 `FORECAST_INVENTORY_TABLE` 接入现势库存表，或调用时显式传 `inventory` |

库存缺失时接口会明确报错说缺哪些 SKU，**不会用 0 兜底**。所以在库存表接进来之前，
订货建议只能带着显式库存参数做验证，不建议给员工当结论用。

默认参数在 `.env` 里：`FORECAST_LEAD_TIME_DAYS`、`FORECAST_BUFFER_DAYS`、
`FORECAST_SERVICE_LEVEL`、`FORECAST_HORIZON_DAYS`。

## 五、LLM 的边界

模型不改数字。`order_suggestion` 和 `forecast_demand` 两个工具的说明里写明了
"你只能解释这份结果，不能改动任何数字"，system prompt 里也再强调一遍。
LLM 的职责是引用区间、库存、在途、交期把这份建议讲清楚，追问缺的参数
（预测周期、服务水平），以及把多 SKU 结果汇总成一页话术。
