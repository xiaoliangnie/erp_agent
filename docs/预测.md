## 1. 要解决什么

采购员真正要的答案是：**该买多少、哪天该下。** 这两件事必须是**同一个决策时点**的输出，不能今天说买 0、同时说第 7 天买 100。

四层必须拆开，禁止混成一句「模型说买 200」：

| 层 | 只回答 | 谁算 |
|---|---|---|
| 预测销量 | 未来可能卖多少（逐日分位） | 模型工件 → 不可变 `forecast_id` |
| 补货输入 | 待发、仓库库存、合格在途、交期、`ruleType` | 镜像库 / 快照 |
| 建议采购量 | 现在该不该下、该买多少 | 确定性公式，**不是模型、不是 LLM** |
| 下单 | 写入 ERP | **关闭** |

LLM 只做意图识别、工具编排和结果解释。不准改数字、不准自己乘天数、不准复述聚水潭「建议/本次采购数」、不准让 `order_suggestion` 内部再 `predict()`。

无库存快照可以报预测，**不能**报正式采购量。库存缺失时报错说明缺哪些 SKU，**不用 0 兜底**。未见过的 SKU 不返回、不拿全局均值兜底。不能把每日 p90 相加当成累计 p90。

## 2. 已拍板（F0，2026-08-18）

这些写进本文后不要再争论。改任何一项等于改口径，必须同步根 `README.md` 和 [`开发.md`](开发.md)。公式细节以 §3 F0.1 为准。

| 项 | 首版取值 |
|---|---|
| 四层 | 预测销量 ≠ 补货输入 ≠ 建议采购量 ≠ 下单 |
| 覆盖窗口 | 唯一字段 `coverage_days` = **`lead_time_days`（从下单到货）**。首版按「每天都可检查并下单」，**不加**检查周期。ERP「备货天数上限」只对照 |
| 分位数 | 维持 **`p10 / p50 / p90`**。Word 方案的 P50/P80/P90 不进调用方 |
| 先销后采 | ERP `ruleType=1`：**不走预测**；公式见 F0.1 |
| 提前采购 | ERP `ruleType=2`：必须带 `forecast_id`；用我们的公式，不抄页面建议数 |
| 粒度 | **SKU × 单仓 × 日**。工件绑定一个 `warehouse_id`；内部 key 用 `WH01::SKU`，对外仍是 `sku_id` + `warehouse_id` |
| 销量 | **销售出库净量**（出库 − 可售退货）。签收 / 支付不做 |
| 业务日 | 东八区 `business_today()` |
| 缺货打标 | 有库存序列再打 `RECENT_STOCKOUT`；没有库存表先不打标，也不把观测销量当成完整需求 |
| 交期缺省 | `FORECAST_LEAD_TIME_DAYS=15`，必须带 `lead_time_source`。默认值只许旁路验证；**正式建议要求 SKU 或供应商级交期** |
| 缓冲缺省 | `FORECAST_BUFFER_DAYS=3` |
| 服务水平缺省 | `FORECAST_SERVICE_LEVEL=0.9` |
| 在途 | 只有 **合格在途**（`EligibleInbound`）能抵扣，见 F0.1 |
| 可用库存 | 必须有库存快照；缺失则报错 |

硬约束：

- 不能把每日 p90 相加当成累计 p90。
- 模型没见过的 key 直接不返回，不要拿全局均值兜底。
- 禁止把 ERP 智能采购建议页的建议数当成系统输出，也禁止拿它的 `LoadPageData` 当训练或日更源。
- `order_suggestion` 最终禁止内部重新预测；读不可变 `forecast_id`。
- 当前不拆独立 Forecast Service。

## 3. F0.1 公式与数据语义冻结（2026-08-18）

F3 改代码之前以本表为准。现有 `service.py` 仍是旧实现（内部 `predict()`、全部在途相减、没有待发），**F1 不改公式**，只按本表做对照和回测。

### 3.1 先销后采（`ruleType=1`）

**不加载预测工件，不调用 `forecast_sales`。**

```
Q = max(0, WaitDelivery − AvailableInventory − EligibleInbound)
```

`EligibleInbound` 不是「所有未入库」：

```
未取消、未完成
SKU 与仓库匹配
预计到货日 ETA ≤ 订单需要日 RequiredDate
状态足够可信
```

没有可靠 ETA 时**不静默扣除**，返回警告 `INBOUND_ETA_UNKNOWN`，该笔不进 `EligibleInbound`。

这是我们的供应链口径，不是 ERP 页面的「待发 − 库存」。对照 ERP 时把差额单独记，不改公式。

### 3.2 提前采购（`ruleType=2`）如何处理待发

训练目标仍是「未来销售出库净量」。待发也是未来可能发生的出库，**禁止** `待发 + ∑p50`（重复计算）。

首版：已知待发是总出库的**下界**，不另加一层。

```
EffectiveDemand_d = max(ForecastP50_d, CommittedOutbound_d)
```

- `ForecastP50_d`：模型预测的当日总出库
- `CommittedOutbound_d`：已知待发按承诺发货日落到当天
- 只有待发总量、没有承诺日：标 `COMMITTED_DATE_UNKNOWN`，按保守规则摊到「今天起、不超过交期」的窗口，并在结果里标明近似

不改训练目标（不去预测「新增订单」）。改目标等于改 F0，另开闸。

### 3.3 `coverage_days` 唯一含义

| 字段 | 含义 | 首版 |
|---|---|---|
| `lead_time_days` | 从下单到货 | 覆盖窗口用这个 |
| `review_period_days` | 两次采购决策间隔 | **不加**。假设每天都可检查 |
| `coverage_days` | 公式里看未来几天 | `= lead_time_days` |

来源优先级：

```
SKU × 供应商 × 仓库专属交期
  → 供应商默认交期
  → FORECAST_LEAD_TIME_DAYS（只许旁路；正式建议拒绝或降级）
```

用默认 15 天时必须带：

```json
{"lead_time_days": 15, "lead_time_source": "system_default", "warnings": ["LEAD_TIME_DEFAULTED"]}
```

「采购周期」一词只出现在 ERP 对照里；我们的代码字段只用 `lead_time_days` / `coverage_days`。

### 3.4 合格在途

与 3.1 同一套 `EligibleInbound`。ETA 晚于需求日的在途不抵扣。没有 ETA 的在途不抵扣，打 `INBOUND_ETA_UNKNOWN`。

当前代码「数量 − 已入库、排除已取消」是**候选池**，不是可抵扣量。F3 之前旁路对照要分开记「全部未入库」和「合格在途」。

### 3.5 建议量和下单日必须同一时点

禁止同时输出「今天建议采购 0」和「第 7 天采购 100」。

逐日投影库存，找到首次低于安全阈值的 `shortage_date`，再算：

```
suggested_order_date = shortage_date − lead_time_days − buffer_days
```

| 情况 | `action` | 数量 |
|---|---|---|
| `suggested_order_date > today` | `not_due` | `order_now_quantity = 0`，`future_quantity = null`，只给 `recommended_review_date` |
| `suggested_order_date ≤ today` | `order_now` | 才算 `recommended_order_quantity` |

`not_due` 不给看似精确的未来采购量——第 7 天的库存、在途和预测都还没发生。

### 3.6 安全库存：现公式只作 Baseline

当前实现：

```
σ_d = (p90_d − p10_d) / 2.5631
SafetyStock = z × √(∑ σ_d²)
```

这假设每日误差正态、对称、互相独立。销量序列通常不独立，会系统性低估累计风险。

F1 必须做交期累计误差回测，产出校准表（至少 7 / 15 / 30 天）。未校准不得过 Gate A。

首版保留现公式，乘上回测得到的 `k_H`：

```
SafetyStock_H = k_H × z × √(∑ σ_d²)
```

样本不足时按销量等级 / 品类 / 间歇性分组共享 `k_H`。直接用经验分位数 `Q_α(∑Actual − ∑P50)` 是升级项，不挡 F1。

### 3.7 缺失日补 0 的前置条件

`dataset.series(key)` 把缺失日补 0，**只有同时满足**才安全：

- SKU 当天在有效销售期（`active_from` ≤ 日 ≤ `active_to`）
- 仓库当天正常运营
- 源系统当天数据完整（`source_day_complete`）
- SKU 当天确实没有出库

未上架、已停用、同步失败、仓库停运、缺货、仓映射未生效：**不能补 0**，应从训练窗剔除或标缺失。否则模型会把「没有数据」学成「销量为零」。

F1 CSV 必须产出：有效期规则、缺失日处理结果。没有这些字段时，训练窗只用「该 SKU 首次出库日～末次出库日」，窗外不补 0。

### 3.8 负净出库

训练目标 `出库 − 可售退货` 可能为负，但推理要求 p10/p50/p90 **全部非负**。

F1 先统计：负净出库日期占比、数量占总量、可售退货比例。

| 情况 | 首版处理 |
|---|---|
| 负值极少 | 标签按日截断 `max(0, 出库 − 可售退货)` |
| 负值较多 | 拆成「预测出库」+「可售退货回流」；另开闸，不在 F1 猜 |

报废、质检中、退回供应商的退货**不能**当可售回流，也不能抵扣需求。

### 3.9 库存快照时效

正式建议必须带 `inventory_snapshot_id` 和 `snapshot_time`。超过允许延迟（F1 先记实测，正式阈值开闸前冻结）则拒绝或明确降级，禁止静默当今日库存。

## 4. 三层设计

```
解析 sku_id + warehouse_id
  → 读取 ruleType / 库存快照 / 待发 / 合格在途 / lead_time
  → ruleType=1：不调预测，按 §3.1
  → ruleType=2：校验 forecast_id + 库存快照 + 交期覆盖 → 按 §3.2–3.5 逐日投影
```

### 4.1 目标工具（F3 之后）

Agent 可见工具**只留这两个**（外加以后的库存/待发查询，按需）：

| 工具 | 风险 | 只回答 |
|---|---|---|
| `forecast_sales` | L0 | 未来可能卖多少；写入 `forecast_runs`，返回不可变 `forecast_id` |
| `order_suggestion` | L0，`decision_impact=high` | 读 `forecast_id`（提前采购）+ 快照，做确定性计算；**禁止再调模型** |

`forecast_demand` 只留代码 / HTTP 兼容别名，**不要注册进 LLM 工具列表**，避免两个近似工具被随机选。

界面必须分行展示：预测结果、补货输入、系统建议、数据风险。不要合成一段普通自然语言当结论。

### 4.2 现在实际挂着的

| 工具 | 代码事实 |
|---|---|
| `forecast_demand` | 已注册 L0；无工件则不可用。F3 改名后从 Agent 目录拿掉 |
| `order_suggestion` | 已注册 L0；内部自己 `predict()`。F3 要拆的就是这个 |
| `forecast_sales` | **未注册** |

库存、待发、`ruleType`、SKU 级交期进来之前，订货建议只做技术验证。

### 4.3 `forecast_id` 是不可变预测结果

不是自增号。至少绑定：

```json
{
  "forecast_id": "fc_xxx",
  "warehouse_id": "WH01",
  "sku_ids": ["SKU1"],
  "as_of_date": "2026-08-18",
  "data_cutoff": "2026-08-17T23:59:59+08:00",
  "horizon_days": 30,
  "model_name": "lgbm-v1",
  "model_version": "2026-08-17-lgbm1",
  "artifact_hash": "sha256:...",
  "predictions": [],
  "skipped": [],
  "status": "success"
}
```

`order_suggestion` 必须校验：id 存在、SKU/仓库一致、日期仍有效、horizon 覆盖交期、结果完整、未被撤回。horizon 小于交期则拒绝或要求重新预测。

审计拆开，不要把采购建议写成一条 `forecast_runs`：

- `forecast_runs`：预测
- `order_suggestion_runs`：建议（`suggestion_id`、`forecast_id`、`inventory_snapshot_id`、`rule_type`、`lead_time_source`、数量与日期）

### 4.4 key 与仓库

单仓首版对外可以只传 SKU，但工件必须写死 `warehouse_id`。请求其他仓库直接拒绝。

内部规范现在就用 `WH01::SKU001`，避免以后多仓把历史串在一起。`predict()` 的 `key` 可以继续是这个内部串；工具入参用独立字段 `sku_id` / `warehouse_id`。

### 5.2 现场规则

员工给 SKU 挂一个**采购模型**（同一商品只能挂一个）。当时账号有 5 条：

| 模型 | 类型 | 在算什么 |
|---|---|---|
| 新品爆款-采购周期计算 | 提前采购 `ruleType=2` | 按采购周期备货 |
| 通勤裤-采购周期计算 | 提前采购 | 同上 |
| 百货-采购周销量计算 | 提前采购 | 按周销量备货 |
| 鞋品-采购周销量计算 | 提前采购 | 同上 |
| 先销后采 | 先销后采 `ruleType=1` | 只补已有订单缺口 |

页面「建议/本次采购数」是他们模型算完的数。日均怎么来、用周期还是上限天数，模型之间不一样。**不抄这个数。**

### 5.3 官方 tip 和现场数字对不上

| 列 | 字段 | 官方 tip |
|---|---|---|
| 订单缺货数 | `outStockQty` | 订单待发数 − 仓库库存 |
| 预测未来订单待发数 | `predFutureOutStockQty` | **备货天数上限 × 预测日均**（先销后采不算） |
| 库存可售天数 | `daysInventory` | （仓库库存 − 订单待发）/ 日均销量 |
| 急缺 | `urgentShortageOrder` | 剩余发货 ≤ 48 小时的待发 − 仓库库存 |
| 预测日均销量 | `salesAvg` | 取所属采购模型，已剔除已取消 |
| 订单待发数 | `waitDeliveryQty` | 以订单占有数为基础 |
| 仓库库存数 | `useStockQty` | 取采购模型的仓库库存设置 |
| 采购周期（天） | `procurementCycle` | 默认供应商从开始采购到货的天数 |
| 备货天数上限 | `max_day` | 最大库存可售天数 |
| 建议/本次采购数 | `purchaseQty` | 页面给员工改的那个数 |

当时约 50 条更接近：`建议采购数 ≈ 预测未来待发 + 订单待发 − 仓库库存`。先销后采退化成订单缺货数。官方 tip 写上限天数 × 日均，现场例子（`BH26700403-00102`：日均 25.7、周期 35、待发 2、库存 0、建议 903）用的是**周期 35 而不是上限 60**。

对照只抽查：我们的交期窗口 `∑p50` vs ERP「预测日均 × 采购周期」。**不要按 60 天去乘，不要拿 `purchaseQty` / `predFutureOutStockQty` 当标签或结论。**

## 6. 当前代码怎么接

调用方只依赖 `backend/forecast/models.py` 的 `Forecaster`。换 Baseline / LightGBM / 分品类实现不改 Agent Core。

仓库里的 `BaselineForecaster`（移动平均 + 星期季节因子）只把链路跑通。

### 6.1 接口

```python
from backend.forecast import Forecaster

class MyForecaster(Forecaster):
    name = "lgbm-v1"
    version = "1"
    granularity = "sku-warehouse-day"
    default_horizon_days = 30

    def fit(self, dataset): ...
    def predict(self, keys, horizon_days, *, start_date=None): ...
```

`predict` 返回 `[{key, date, p50, p10, p90}, ...]`。`p10 ≤ p50 ≤ p90` 且非负；没见过的 key 不返回；`p90 − p10` 必须是真区间。

`dataset.series(key)` 的补 0 规则以 §3.7 为准，不能无条件补。

### 6.2 存取与特征状态

**A. JSON 参数**（Baseline）：`state()` / `restore()` → `model.json`。

**B. 二进制权重**（LightGBM）：重写 `save()` / `load()`。

树模型不能只有 booster。`predict(keys, horizon_days, start_date)` **不传入**最新销量，所以工件必须自带特征快照：

```
<version>/
  metadata.json
  model.bin
  feature_state.parquet
  calibration.json
  known_keys.json
```

每天（或每个业务批次）：刷新销售 → 重建特征状态 → 训练或刷新工件 → 原子切换 latest。`metadata` 至少有 `data_cutoff`、`training_start` / `end`、`feature_snapshot_time`、`artifact_hash`、`warehouse_id`。过旧则警告或拒绝 `STALE_MODEL_DATA`。

不改 `Forecaster` 调用签名的前提下，**每日生成带最新特征状态的工件**是正路。

### 6.3 训练

```bash
.venv/bin/python scripts/train_forecast_model.py --csv D:/Predict_DATA/csv/销售出库明细.csv
.venv/bin/python scripts/train_forecast_model.py \
    --csv D:/Predict_DATA/csv/销售出库明细.csv --forecaster mymodels.lgbm:LgbmForecaster --holdout-days 14
```

F1 训练数据目录是本机 **`D:\Predict_DATA`**（`FORECAST_EXPORT_DIR`），在仓库外，不进 git、不进镜像库。出库接口的 `sku_id` **不能减少页数**，一年数据靠晚上挂 `拉一年并训练.cmd`（可续跑）。对照某品类时再筛日汇总，不要按 SKU 重拉。`csv/windows/` 是断点，`csv/销售出库日汇总.csv` 给训练。

### 6.4 树模型：直接多步，不要递归

F2 不要「预测第 1 天再当第 2 天 lag」。训练样本带 `horizon = 1..30`，目标 `y_{t+h}`，分别训 p10 / p50 / p90，预测后：

```python
p10 = max(0, p10)
p50 = max(p10, p50)
p90 = max(p50, p90)
```

一次给出完整曲线，符合现有 `predict()`，不改 Agent Core。

F2 晋级不能只看 MAE。至少比：WAPE、Bias、日级 p10/p90 覆盖率、交期累计误差覆盖率、SKU 覆盖率、销量等级、库存仿真缺货率 / 平均库存 / 紧急采购次数。仿真不劣于 Baseline 才换生产工件。

### 6.5 当前订货公式（旧实现，仅 Baseline / 旁路）
