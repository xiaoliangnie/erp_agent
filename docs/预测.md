# 上半：当前代码怎么接

调用方（订货建议、`/api/forecast/*`、Agent 工具）只依赖 `backend/forecast/models.py` 里的
`Forecaster` 接口。**换模型实现不需要改任何调用方代码**，也不需要改 Agent Core。

当前仓库里的 `BaselineForecaster`（移动平均 + 星期季节因子）只是把链路跑通用的占位实现，
可以直接替换。

## 要实现的接口

```python
from backend.forecast import Forecaster

class MyForecaster(Forecaster):
    name = "lgbm-v1"          # 会写进每次订货建议的审计记录
    version = "1"             # 训练时通常在 fit() 里改成带日期的版本号
    granularity = "sku-day"   # 仅作说明，接口本身不预设粒度
    default_horizon_days = 30

    def fit(self, dataset): ...
    def predict(self, keys, horizon_days, *, start_date=None): ...
```

### `fit(dataset)`

`dataset` 是 `DemandDataset`：

| 成员 | 说明 |
|---|---|
| `dataset.records` | `[{"key": "SKU", "date": "2026-08-11", "qty": 12.0}, ...]`，已按 key + date 排序 |
| `dataset.keys` | 全部 key |
| `dataset.series(key)` | 该 key 的逐日序列，**缺失日已补 0** |
| `dataset.start` / `dataset.end` | 数据窗口 |
| `dataset.summary()` | 行数、key 数、窗口、总量，会写进工件元数据 |

历史不足、数据为空这类情况请抛 `ForecastError`，不要静默返回一个空模型。
建议在 `fit()` 结束时把 `self.version` 设成可追溯的值（例如 `f"{dataset.end}-lgbm1"`）。

### `predict(keys, horizon_days, *, start_date=None)`

必须返回逐 key 逐日的列表：

```python
[{"key": "SKU-1", "date": "2026-08-11", "p50": 13.4, "p10": 7.2, "p90": 19.7}, ...]
```

三条硬约束，破坏了订货建议就会算错：

1. `p10 ≤ p50 ≤ p90`，且都 **不为负**；
2. **模型没见过的 key 直接不返回**，不要拿全局均值兜底——上层会把它列进 `skipped` 并告诉员工；
3. `p90 − p10` 是真实的不确定性区间。安全库存就是用 `σ = (p90 − p10) / 2.5631` 折算的，
   区间给太窄会系统性低估安全库存。

下半目标契约用 `P50/P80/P90`。**改调用方之前先定一种**，不要两套分位数并存。

### 存取：两种做法，选一种

**A. 参数能 JSON 序列化**（推荐）：只实现 `state()` / `restore()`，基类写成 `model.json`。

**B. 二进制权重**（LightGBM booster、joblib、torch）：直接重写 `save()` / `load()`。

另外建议实现 `known_keys()`：员工问到没有历史的 SKU 时，上层能提前说清楚。

## 训练并落工件

```bash
.venv/bin/python scripts/train_forecast_model.py --csv 销量明细导出.csv
.venv/bin/python scripts/train_forecast_model.py \
  --csv 销量明细导出.csv --forecaster mymodels.lgbm:LgbmForecaster --holdout-days 14
.venv/bin/python scripts/train_forecast_model.py --days 365 --forecaster mymodels.lgbm:LgbmForecaster
```

工件落在 `FORECAST_MODEL_DIR/<version>/`（默认 `files/data/models/`，已 gitignore）。
`metadata.json` 里的 `forecaster` 字段是 `模块:类名`，**这是唯一耦合点**。

服务端惰性加载最新工件，不需要重启：`/api/forecast/status` · `/predict` · `/reload`。
每次订货建议记进 `forecast_runs`。

## 订货建议还缺什么

```
建议下单量 = 交期内预测需求(∑p50) + 安全库存(z×√∑σ²) − 可用库存 − 在途待入库
建议下单日 = 需求缺口出现日 − 供应商交期 − 缓冲天数
```

| 输入 | 现状 |
|---|---|
| 预测需求 / 区间 | 模型工件 |
| 在途待入库 | **已可用**（数量 − 已入库，排除已取消单） |
| 可用库存 | **还没有数据源**。配 `FORECAST_INVENTORY_TABLE`，或调用时显式传 `inventory` |

库存缺失时明确报错，**不会用 0 兜底**。库存表进来之前，不要把订货建议当员工结论。

LLM 不得改 `order_suggestion` / `forecast_demand` 返回的任何数字。

# 下半：下一阶段目标

由《多商品销量预测模型训练与部署实施方案》+《Agent 销量预测工具功能设计文档》合并。
不替代上半的代码事实。

## 原则

| 原则 | 要求 |
|---|---|
| 职责分离 | 预测 ≠ 采购建议 ≠ 下单 |
| 数字忠实 | Agent 不得改、补、猜工具返回的数字；补货工具优先收 `forecast_id` |
| 时间安全 | 特征只准用 `as_of_date` 当时已存在的数据，禁止随机切分 |
| 销量 ≠ 需求 | 缺货时观测销量是需求下界，必须打标 |
| 可追溯 | 成功响应必须带 `forecast_id`、模型版本、`data_cutoff_time` |
| 安全降级 | 无受控结果时停止输出数字 |

## 模型底座

| 决策 | 首版方案 |
|---|---|
| 范围 | 多 SKU × 多地点的全局模型 |
| 粒度 | SKU × 仓库/门店 × 日 |
| 目标 | 累计需求 + 每日需求 |
| 输出 | P50 / P80 / P90 |
| 算法 | CatBoost 或 LightGBM 分位数 |
| 部署 | 每日批量预计算 + 实时情景推理 |
| 基线 | 季节朴素、移动平均必须先算 |

**不能把每日 P90 相加当成累计 P90。** 采购必须用直接训练的累计分位数。

最低数据：日销售（含退货）、日库存/缺货、商品与地点主数据、计划价格/促销、日历。
缺货打 `RECENT_STOCKOUT`；严重缺货样本剔除或降权。样本按 as-of 构造，禁止未来泄漏。

成功门槛先算真实基线再冻结，不要空口写 WAPE ≥5%。晋级还要过库存仿真，不只看 MAE。

Forecast Service 独立于 Agent：Agent 不加载模型文件、不直接读特征表。
日常走缓存；促销/改价才实时情景。

## Agent 工具 `forecast_sales`

现有工具注册表里的一条 **L0 只读**工具，不是新 Agent。Gate A 之前只训不注册。

| 用户在问 | 调用 |
|---|---|
| 未来两周卖多少、八折会多卖多少 | `forecast_sales` |
| 该采购多少、哪些会缺货 | `forecast_sales` 只是工作流里的一环 |
| 上月实际销量、当前库存、采购单何时到 | **不要**调用 |

采购参考顺序写死在状态机：

```
解析商品地点 → 补货策略
→ forecast_sales + 库存（可并行）
→ calculate_replenishment(forecast_id, inventory_snapshot_id, policy)
```

无库存快照可以报预测，**不能**报正式采购量。
平台注入 `tenant_id` / `user_id` / 地点范围，禁止模型填写。

风险标记必须展示：`RECENT_STOCKOUT`、`NEW_SKU`、`STALE_FEATURE_DATA`、`OUT_OF_DISTRIBUTION_SCENARIO`、`MODEL_FALLBACK`。
降级：同版本缓存 → 标明的基准缓存 → seasonal naive（打 fallback）→ 停止出数。
