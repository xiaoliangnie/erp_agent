# 商品资料与图片入库

> 状态更新（2026-08-13）：供应链代理已开放 `items.query`，商品主数据已接入
> `realtime_products`。镜像保存商品大小图 URL，并继续异步缓存到 `data/product-images/`；
> 没有把平台原始大图 BLOB 写进 MySQL。本文后半保留未来“小图二进制权威入库”的设计参考。

## 1. 现状（2026-08-12 实测）

### 采购接口仍不带图片，商品接口已经补齐主要图片来源

| 数据源 | 明细行数 | `image_url` 有值 | 有图 SKU 数 |
|--------|---------|-----------------|------------|
| `orders/search` 订单明细 | 17,916 | 17,309（96.6%） | 2,301 |
| `purchase/orders/query` 采购明细 | 81,843 | **0** | 0 |

代理现已开放 `items.query` 和 `suppliers.query`。`items.query` 返回 SKU、款式、名称、规格、分类、
品牌、单位、供应商、价格、启停状态、扩展字段及 `pic_big`/`pic`；采购接口自身仍没有图片键。
首次接入已优先批量补齐订单/采购明细引用过的 SKU，后续按 `modified` 持续增量。

### 落到合同上的覆盖率

镜像同步会把订单侧的有效图片下载到 `data/product-images/`，合同生成的第三级回退正好读同一目录，
所以这部分已经自动生效。但采购的 SKU 空间远大于近期订单的 SKU 空间：

| 生成合同的范围 | 涉及 SKU | 有缓存图 |
|---------------|---------|---------|
| 最近 30 天的采购单 | 2,405 | 744（31%） |
| 本年度采购单 | 6,838 | 1,740（25%） |
| 全部年份 | 16,085 | 1,924（12%） |

只采购过、近期没出单的款不会出现在订单接口里，所以这条路存在天花板，与代码无关。

### 图片散在 17 个平台 CDN 上，尺寸压不下来

订单明细的 `pic` 是各网店的平台主图，不是聚水潭自己托管的商品图。去重后 2,001 个地址的分布：

| CDN | 占比 | URL 参数能否拿小图 |
|-----|-----|------------------|
| 有赞 `img.yzcdn.cn` | 23% | 规则与 OSS 不同 |
| 抖店 `p9/p3-aio.ecombdimg.com` | 38% | 试过 `~tplv-obj:320:320.image`、`~320x320.image`、`imageMogr2`，全部 404 或原样返回 |
| `images-erp.sursung.com` | 16% | 未知 |
| 微信 / 淘宝 / 小红书 / 快手 / 京东 / 拼多多 | 合计 17% | 每家一套 |
| 聚水潭 `oss.scm321.com` | **6%** | 支持 `x-oss-process`，实测 98 KB → 6 KB |

本地缓存现状：2,275 张 / 777 MB，平均 348 KB，中位 232 KB，最大 9 MB。

### 容量约束

镜像库现在 391 MB（`realtime_purchase_order_items` 141 MB 最大），跑在 InnoDB buffer pool 只有
128 MB 的 ECS 上。按平均 348 KB 把 16,085 个采购 SKU 的原图全量入库约 **5.5 GB**，库体积翻十几倍，
图片页会把看板年度查询（现在 6–8 秒）需要的数据页反复挤出缓存。**原图全量入库不可行。**

## 2. 现有链路（已实现，本文不改其形状）

```
config/products.json 的 image_path        ← 第一级，手工维护，目前只有 1 条
config/product-images/<SKU|款式>.<后缀>    ← 第二级，手工放图
data/product-images/<SKU|款式>.<后缀>      ← 第三级，API 同步与 ERP Worker 共用目录
```

`backend/product_images.py` 的 `resolve_product_image()` 按上面三级找文件，命中即返回**本地绝对路径**；
全部未命中时返回 `status="missing"`，**不抛错**，合同照常生成，Excel 里写「暂无图片」。

`backend/contract_workbook.py` 只接受本地绝对路径（openpyxl 内嵌；webp 会先转 png），
支持 `.png/.jpg/.jpeg/.webp`。**这个契约不变**：即使权威存储进了数据库，生成前也要落一份本地文件。

## 3. 决策

1. **权威存储放镜像库，本地目录降级为读穿缓存。** 图片跟着库走，服务换机器、重装不丢，多个员工共用一份。
2. **全量入库，只存小图一档。** 目标每张 10 KB 量级，全量约 100–300 MB，与库现有体积同量级。
3. **商品资料与图片分两张表。** 资料表要被合同和看板频繁 JOIN，二进制列不能被顺带 `SELECT *` 带出来；
   两者的更新频率也不同（资料随主数据变，图片一次抓完基本不动）。
4. **主数据以 SKU 为主键、款式编码为次级索引**，与 `resolve_product_image` 现有的「先 SKU 后款式」一致。
5. **手工配置优先级高于抓取来的资料。** `config/products.json` 是刻意覆盖用的，抓取只填空缺。

### 尺寸策略取决于接口返回的图片 host（待定）

- 若商品资料接口返回 `oss.scm321.com`（聚水潭自己 OSS 托管，样本支持缩放）：
  加 `?x-oss-process=image/resize,w_320/format,jpg/quality,q_80`，白拿 6–8 KB 一张，
  16,085 张约 **100–130 MB**，不引入任何新依赖。**优先走这条。**
- 若返回的是平台 CDN（像现在订单侧那样散在 17 家）：URL 参数无法统一，要拿小图只能服务端解码缩放，
  需要引入 Pillow（320 px / JPEG q80 约 10–20 KB，全量 160–320 MB）。
  合同写入器已经为内嵌 png/jpg/webp 引入了 Pillow，**批量缩放商品图仍要单独确认**，不要顺手拿它去压 1.6 万张。
- 兜底约束：无论哪条路，入库前按 `PRODUCT_IMAGE_MAX_BYTES` 拒绝超大图并记原因，不静默存 9 MB 的原图。

## 4. 表结构草案

两张表都建在镜像库（`hanli.env`），DDL 跟着 `backend/realtime_mirror.py` 的 `SCHEMA_SQL` 一起管理，
保持「建表只在一处」。

```sql
CREATE TABLE IF NOT EXISTS `realtime_product_master` (
    sku_id        VARCHAR(128) NOT NULL PRIMARY KEY,   -- 商品编码，抓取与合同的对应键
    i_id          VARCHAR(128) NOT NULL DEFAULT '',    -- 款式编码，次级匹配
    name          VARCHAR(255) NOT NULL DEFAULT '',
    properties_value VARCHAR(255) NOT NULL DEFAULT '', -- 颜色及规格
    category      VARCHAR(128) NOT NULL DEFAULT '',
    brand         VARCHAR(128) NOT NULL DEFAULT '',
    unit          VARCHAR(32)  NOT NULL DEFAULT '',    -- 合同「单位」，缺省时合同仍回退「个」
    packaging     VARCHAR(255) NOT NULL DEFAULT '',
    material_process VARCHAR(255) NOT NULL DEFAULT '', -- 材质工艺
    national_code VARCHAR(64)  NOT NULL DEFAULT '',    -- 国标码
    supplier_sku_id VARCHAR(128) NOT NULL DEFAULT '',
    image_source_url VARCHAR(2048) NOT NULL DEFAULT '',
    modified      DATETIME NULL,                       -- 接口侧修改时间，增量水位用
    source_payload JSON NULL,
    api_synced_at DATETIME NOT NULL,
    KEY idx_master_style (i_id),
    KEY idx_master_modified (modified)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS `realtime_product_images` (
    sku_id       VARCHAR(128) NOT NULL PRIMARY KEY,
    i_id         VARCHAR(128) NOT NULL DEFAULT '',
    variant      VARCHAR(16)  NOT NULL DEFAULT 'w320', -- 尺寸档位，换档能整表重灌
    content_type VARCHAR(64)  NOT NULL DEFAULT '',
    byte_size    INT UNSIGNED NOT NULL DEFAULT 0,
    checksum     CHAR(64)     NOT NULL DEFAULT '',      -- sha256，判断是否需要重写本地缓存
    source_url   VARCHAR(2048) NOT NULL DEFAULT '',
    source       VARCHAR(32)  NOT NULL DEFAULT 'api',   -- api / erp_worker / manual
    image        MEDIUMBLOB   NULL,                     -- 16 MB 上限，够用且比 LONGBLOB 省一字节长度头
    fetched_at   DATETIME NOT NULL,
    error_message VARCHAR(500) NOT NULL DEFAULT '',     -- 抓失败也留行，避免每次合同重试同一张
    KEY idx_image_style (i_id),
    KEY idx_image_fetched (fetched_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

要点：

- `image` 允许为 NULL：抓失败或被尺寸上限拒绝时留一行带 `error_message`，合同层看到就直接判缺图，
  不再每次生成都重试同一个坏地址。
- 读取一律显式列名，**禁止 `SELECT *`**，否则会把二进制拖进 buffer pool。
- `variant` 是整表重灌的开关：将来想换 `w480`，按 `variant <> 当前档` 找出要重抓的行即可。

## 5. 回退优先级（实现后）

`resolve_product_image()` 从三级变四级，新级插在最后，保证手工维护仍然最高优先：

| 优先级 | 来源 | 说明 |
|-------|------|------|
| 1 | `config/products.json` 的 `image_path` | 手工指定，最高 |
| 2 | `config/product-images/<SKU\|款式>` | 手工放图 |
| 3 | `data/product-images/<SKU\|款式>` | 本地缓存（含 Worker 上传、旧 API 下载） |
| 4 | 镜像库 `realtime_product_images` | **新增**：命中后把二进制写进第 3 级目录，再返回该路径 |

第 4 级是**读穿缓存**：查库拿到二进制 → 落 `data/product-images/<SKU>.<后缀>` → 返回本地绝对路径。
后续同 SKU 直接在第 3 级命中，不再查库；合同写入器「只吃本地路径」的契约因此不用改。
落盘沿用 `cache_product_image()` 的临时文件 + `replace()` 原子替换，避免并发生成时读到半截文件。

## 7. 明天接口到位后要先确认的事

1. 路由与分页参数（是否同样是 `page_index` / `page_size` / `modified_begin`），单页上限是否也是 50。
2. 返回的图片字段名与 **host**——直接决定第 3 节走哪条尺寸策略，也决定要不要加 Pillow。
3. 是否给款式级（`i_id`）图片，还是只有 SKU 级；如果只有款式级，落盘与查表都要按款式再兜一层。
4. 有没有国标码、包装、单位、材质工艺这几个合同要用的字段；没有的话这些仍留在 `config/products.json`。
5. 全量拉一遍 16,085 个 SKU 需要多少次请求，与代理 60 次/分钟的限流一起算出回灌耗时。

## 8. 明确不做

- 不改合同图片输入契约（仍只接受本地绝对路径，不接 URL 或 base64）。
- 不为 17 家平台 CDN 各写一套缩放规则。
- 缺图不阻断合同生成——保持现在「写『暂无图片』照常出合同」的行为，与供应商、单价缺失必须中止的口径区分开。
- 不下线 ERP Worker 抓图链路：接口覆盖不到的老款仍要靠员工登录态补。
