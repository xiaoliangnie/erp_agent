# 采购供应链 Agent 项目：本期开发与架构演进任务提示词

## 0. 你的角色

你是一名负责本项目持续演进的高级软件架构师 + Senior Backend Engineer。

你的任务不是从零重写项目，也不是为了使用某个 Agent Framework 而强行迁移现有代码。

你需要：

1. 先理解当前仓库、现有业务能力和架构文档；
2. 保留已经稳定运行的业务链路；
3. 按本文定义的边界逐步演进 Agent Runtime；
4. 所有新增设计都必须考虑后续 Web 多用户、钉钉 Gateway、ERP AI 服务账号、RAG/询报价、权限控制和可审计执行；
5. 但**不得提前实现本文明确标记为“本期不做”的能力**。

工作原则：

> 小步演进、保持兼容、场景驱动、确定性业务优先、Agent 只处理真正需要语言理解和动态编排的问题。

* SKU 换货 dry-run 与 ERP 操作验证；
* Forecast 接口骨架；

当前核心架构思想继续保留：

# 4. 用户名称归一化

ERP 中同一个人可能存在：

```text
阿飞
张三
阿飞（张三）
张三（阿飞）
阿飞(张三)
张三 ( 阿飞 )
```

这些记录可能实际属于同一个员工。

需要实现独立的：

```text
normalize_staff_name()
```

或等价模块。

归一化至少处理：

* 中文括号；
* 英文括号；
* 前后空格；
* 括号前后空格；
* 花名 + 真名；
* 真名 + 花名；
* 重复空格；
* 全角/半角基础差异。

但是：

> 不允许仅凭模型猜测两个人是不是同一个人。

不能确定的映射必须进入：

```text
needs_review
```

等待人工确认。

# 5. User 数据模型

当前阶段优先使用一张 User 主表，不急于拆复杂 IAM。

推荐至少包含：

```text
users
```

字段建议：

| 字段                | 说明                                        |
| ----------------- | ----------------------------------------- |
| user_id           | 内部永久唯一 ID                                 |
| real_name         | 真实姓名，可为空                                  |
| nickname          | 花名，可为空                                    |
| canonical_name    | 系统内部标准名称                                  |
| display_name      | 默认显示名称                                    |
| erp_buyer_aliases | ERP 中已确认属于这个人的所有采购员写法                     |
| dingtalk_userid   | 后续钉钉绑定                                    |
| dingtalk_unionid  | 预留                                        |
| mobile            | 手机号                                       |
| department        | 部门                                        |
| status            | active / disabled                         |
| source            | purchase_order_seed / manual / dingtalk 等 |
| created_at        | 创建时间                                      |
| updated_at        | 更新时间                                      |

如果当前数据库不方便保存数组，可以使用：

```text
erp_buyer_aliases_json
```

第一阶段允许采用 JSON 字段。

不要为了理论上的三范式立刻拆：

```text
users
user_aliases
user_identities
user_departments
```

等多张表。

等实际需要多 Provider 身份后再迁移。

# 6. User ID 的原则

`user_id` 不得直接使用：

```text
张三
阿飞
手机号
钉钉 userId
```

作为主键。

使用稳定内部 ID，例如：

```text
usr_xxxxxxxxx
```

原因是外部身份可能变化，而内部业务记录必须长期稳定。

未来所有：

```text
Session
Workflow
PendingAction
Audit
Artifact
ERP Command
Memory
```

最终都应该引用：

```text
user_id
```

而不是自由文本：

```text
operator="张三"
```

# 11. P1：自然语言 Intent Router

本轮可以建立第一版 Intent Router。

不要直接把所有自然语言都送给主 Agent Loop，让 Agent 自己探索工具。

目标架构：

```text
User Message
      ↓
Deterministic Command Rules
      ↓
Intent Router
      ↓
Agent / Query / Workflow / RAG
```

Intent Router 输出统一结构，例如：

```json
{
  "route": "exact_query",
  "domain": "procurement",
  "operation": "get_purchase_order",
  "entities": {
    "po_id": "604264"
  },
  "missing_slots": [],
  "risk_level": "L0",
  "confidence": 0.98
}
```

route 第一阶段至少考虑：

```text
exact_query
workflow
agent
knowledge
clarify
deny
```

未来扩展：

```text
document_rag
graph_query
mixed
```

---

# 12. Intent Router 的实现顺序

优先级：

```text
1. 确定性命令
2. 单号/实体规则
3. 关键词或轻量语义匹配
4. LLM Structured Output
5. 低置信度追问
```

例如：

```text
“604264 到货了吗”
```

应该直接解析：

```text
procurement.get_purchase_order
```

而不是先让通用 Agent 思考十几步。

而：

```text
“看看最近采购有什么需要我注意的”
```

可以进入：

```text
agent
```

执行开放式只读分析。

---

# 13. Intent 与权限严格分开

即使 Intent Router 输出：

```text
create_purchase_order
```

也不代表用户有权限执行。

未来完整路径必须是：

```text
Intent
   ↓
Permission
   ↓
Business Validation
   ↓
Impact Analysis
   ↓
Preview
   ↓
Approval
   ↓
Execute
```

Intent Router 只负责：

```text
“他想干什么”
```

不负责：

```text
“他有没有资格干”
```

# 19. Memory 必须先区分五种概念

不要把它们全部叫 Memory：

```text
Session History
当前会话原始历史

Working Context
本次真正发送给模型的内容

Session Summary
被压缩的旧会话

User Memory
跨会话稳定用户信息

Business State
ERP / Workflow 的真实业务状态
```

业务状态绝对不能依赖 Memory。

---

# 20. 本项目推荐的 Memory 方向

重点评估这种架构：

```text
Session Event Log
      │
      ├── Context Surface
      │
      └── Session Summary

User Memory
      │
      └── SQL 结构化存储

Task / Episodic Memory
      │
      └── workflow / business object 关联

Knowledge
      │
      └── RAG
```

第一阶段不需要“无限记忆”。

需要解决的是：

```text
上下文不会无限膨胀
用户之间不会串线
服务重启可以恢复
业务操作可追溯
用户稳定偏好可以保留
动态 ERP 数字不会进入长期记忆
```

# 31. 钉钉 Gateway

参考 Hermes 等 Gateway 架构。

原则：

```text
一个企业机器人
+
多个业务场景
+
多个个人 Session
```

不要为：

```text
催单
查询
换货
询价
品控
```

分别创建 Agent Runtime。

Gateway 负责：

```text
消息接入
用户解析
session_key
消息幂等
群策略
结果可见范围
路由
```

# 32. 用户隔离

钉钉群内不能使用：

```text
整个群共享一个 Agent Session
```

应该使用：

```text
tenant
+
channel
+
conversation
+
user_id
+
epoch
```

形成个人会话。

例如：

```text
group_purchase
  ├── 张三 Session
  ├── 李四 Session
  └── 王五 Session
```

但是他们可以共同操作：

```text
po_id
o_id
rfq_id
workflow_id
```

等共享业务对象。

也就是说：

> 聊天上下文属于个人，业务对象属于团队。

# 37. 每个场景必须至少验证

## Happy Path

正常业务是否成功。

## Parameter Validation

缺少参数、非法参数是否正确阻止。

## User Isolation

张三的会话和李四是否串线。

## Permission Boundary

如果当前权限体系尚未完成：

```text
至少确认未来权限检查有明确入口
```

## Idempotency

重复请求是否产生重复业务动作。

## Recovery

中途失败后是否可恢复或明确进入失败状态。

## Audit

是否能事后回答：

```text
谁
什么时候
通过什么入口
让 Agent
调用什么工具
对什么业务对象
执行了什么
结果是什么
```

# 38. Golden Dialogue

已有 Golden Dialogue 测试必须保留并持续增加。


必须能区分：

```text

```

# 47. 完成标准

本轮不是“代码写出来”就算完成。

必须满足：

* 现有测试全部通过；
* 新增 User 测试通过；
* 已有员工身份链路没有被破坏；
* 同一采购员不同合法别名可以解析到同一 `user_id`；
* 无法确定的别名不会自动合并；
* 钉钉字段已经预留；
* 后续 Web 用户可以复用同一 User；
* Intent Router 如果实现，有独立测试；
* 所有 Deferred 能力在文档中有明确标签；
* 不出现“文档写已实现、代码实际没实现”的状态漂移；
* 不为了架构调研重写当前稳定业务模块。
