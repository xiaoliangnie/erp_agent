## 1. 原则

1. **薄 Agent + 确定性工具。** LLM 只理解意图、补齐参数、选工具、组织回答。查库、计算、生成文件、权限、ERP 写入、通知全部走普通代码。
2. **能写成固定步骤的不要做成开放 Agent。** 看板、台账、合同、催办、换货执行走页面或定时任务；对话只覆盖路径不确定的问句。
3. **实时业务数字禁止 RAG。** 库存、交期、付款、订单状态必须 Exact Query。RAG 只留给 SOP / 制度 / 历史资料，且验证后再做。
4. **缺数据就停。** 合同、订货建议、预测都不用 0 或占位信息兜底。
5. **数字忠实。** Agent 不得改、补、猜工具返回的数字。预测 ≠ 采购建议 ≠ 下单。
6. **高风险必须闭环。** 影响分析 → 预览 → 确认/审批 → 执行 → 回读核验。L1/L2 谁发起谁确认，不按金额自动放行。
7. **身份跟员工走。** Web 和钉钉落到同一个 `user_id`。共享 Token 只做传输鉴权，不代表操作员。
8. **不让模型写 ERP、不让模型开浏览器。** Playwright / userscript 只做类型化命令的 Provider。
9. **第一阶段继续单仓库、单应用库（SQLite）、单进程多线程。** 迁 MySQL / 拆进程是专用机器之后的事。
10. **增量演进，不重写。** 新能力用 Adapter 接现有 `tools.py` / `pending_actions` / 镜像库。

## 6. S1 身份与会话（Gate A）

目标：Web / 钉钉 / CLI 共用一个 `user_id`，会话不串线，工具能按人做最小权限判断。

**最小实现，不做登录产品、不做权限 Studio。**

| 项 | 落地 | 不要做成 |
|---|---|---|
| `RequestContext` | **已做**：`user_id` / `trace_id` / `role` / `buyer_names`，写入审计与待确认动作。有钉钉绑定则 Web/钉钉同一 `user_id` | 前端自由填姓名当身份；完整 `users` 表下一迭代 |
| 统一身份 | 仍用 `staff_bindings` 解析，不新建 `users` 表 | 先做完整账号体系 / SSO |
| 角色 | **已做**：`viewer` / `operator`；viewer 不能 L1/L2，拒绝带结构化 `permission` | 按金额自动放行、复杂 RBAC |
| 数据范围 | **已做**：「我名下」只看绑定采购员署名；空 buyer 仍看全部 | 店铺/分类/财务级矩阵 |
| 会话 S1 | **已做**：epoch、空闲翻篇、显式重置、同会话串行锁、悬空 `tool_calls` 剔除 | 多个机器人分流上下文 |
| 会话 S2 | **已做**：字符预算、工具信封、usage 写入 `agent_runs` | 先做滚动摘要（数字会陈旧） |
| ToolSpec | **已做**：注册表补 `permission` / `side_effect` / `channels` | 动态发现 ERP 全量对象 |

过门：

- Web 和钉钉同一人，`user_id` 一致，审计不再只记自由文本姓名
- 同会话并发消息串行，不交叉执行
- 空闲翻篇后「上一张单」不会指到昨天
- 未绑定用户不能做 L1/L2
- 工具权限拒绝时有结构化原因，不靠 prompt 拦

详见 V5 §5、[`architecture/会话与钉钉.md`](architecture/会话与钉钉.md) §11。

## 7. S2 工作项与执行内核（Gate B）

目标：待确认、执行中、失败不再只活在聊天记录里。HTTP 不跑长任务。

| 项 | 落地 | 不要做成 |
|---|---|---|
| Work Item | 一张 `work_items` 表，包住现有 `pending_actions`、换货任务、品控待办 | 复杂 BPM、跨部门 SLA |
| `/workbench` | 新路由：列表 + 详情 + 确认/取消；钉钉卡片只做提醒和轻确认 | 把聊天改成主工作台 |
| Impact Analysis | **先只做换货**：库存、履约、重复单、金额，确定性规则 | 通用 DSL、LLM 写影响规则 |
| Job | 合同转 PDF、催办群发、镜像同步等长任务入队；HTTP 只创建 Job | 每请求新线程、Scheduler 直接干重活 |
| Outbox | 钉钉出站投递台账：生成成功但发送失败可恢复，语义 at-least-once 且可提示重复 | 在聊天消息里推断是否已发送 |
| 预览冻结 | `pending_actions` 的 preview 入参与 execute 入参不可漂移（现有测试继续加硬） | 确认时允许模型改参数 |

过门：

- 换货 / 合同确认在 `/workbench` 和原会话都能完成，状态只存一份
- Preview 与 Execute 参数不一致直接拒绝
- 换货 Impact 有 unittest（至少：重复任务、目标 SKU 不存在、跨店）
- 进程在「已生成回复、未发出」处重启，不重跑工具，只补发或标记未知

V5 的 Workflow Runtime 本期 = **现有确认状态机 + Job + Work Item**，不新写一套编排引擎。

## 10. F 预测旁路（不挡主线）

预测是中长期能力。**S1 完成前只做数据和模型，不注册新 Agent 工具。**
目标契约和接入步骤见 [`预测.md`](预测.md)。

| 步 | 做什么 | 和现有代码 |
|---|---|---|
| F0 口径 | 冻结：销量定义（出库/签收/净销）、缺货、业务日、SKU 与地点 ID；分位数统一（现接口是 `p10/p50/p90`，方案是 `P50/P80/P90`，**改调用方前先定一种**） | 表名已是 `FORECAST_SALES_*` / `FORECAST_INVENTORY_*` |
| F1 基线 | 训练快照 + 季节朴素 / 现有 `BaselineForecaster`；没有基线不承诺「改善 5%」 | `scripts/train_forecast_model.py --csv` |
| F2 树模型 | 实现 `Forecaster`（LightGBM/CatBoost 分位数）；滚动时间回测；缺货打标 | 耦合点只有 `metadata.json` 的 `forecaster` |
| F3 工具拆分 | Gate A 之后：新增 L0 `forecast_sales`（只读预测）；`order_suggestion` 改为收 `forecast_id` + 库存快照，不再 internally 兼当预测入口 | 库存仍缺失则只报预测、不报采购量 |
| F4 服务化 | 批量预计算、`forecast_id` 回查、一个促销情景 | 现有 `/api/forecast/*` 扩契约，不先拆独立进程 |

成功门槛先算真实基线再冻结，不要把方案里的 WAPE ≥5% / P90 覆盖 85%–93% 空口写进验收。

硬约束继续有效：不能把每日 P90 相加当累计 P90；LLM 不得改写分位数；无库存快照不得出正式建议量。
